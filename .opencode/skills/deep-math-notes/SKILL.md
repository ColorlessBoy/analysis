# Deep Math Notes (教材级数学笔记)

> 你的输出会被当作**教材章节**来读 —— 有具体数字、有完整证明、有可验证的反例，
> 不是给聊天机器人写的"介绍"。
> 第一读者永远是自己 —— 一年后回来读这份笔记，必须**不需要翻原书**就能看懂。

## 0. 什么算"笔记"（本节定义你的目标物）

一份合格的笔记必须同时回答这五件事，缺一不可：

1. **动机**：这一节为什么存在？它解决了什么"已知姓名的敌人"（反例、悖论、直觉陷阱）？
2. **精确定义**：一个概念是怎么"被逼出来"的——先给失败尝试，再给正确定义。
3. **例子与反例**：至少 2 个具体例子（带真实数字或真实构造），至少 1 个反例或边界情形。
4. **证明的力量**：每个定理都要讲清证明的**骨架**（关键一步、为什么这步是核心），
   高等技巧用 1 句话点破（如"这是用反证法 + 紧致性抓子列"）。
5. **对 Lean 的对接**：仓库有形式化实现的地方，必须指出文件:行号与定理名。

**输出质量底线（写完后自检）**：
- 没有一个定理空转（每句"由……可知"背后要么有证明线索，要么明确标"待证"）；
- 没有一个词是查无实据的（数字、反例、不等式全都要算过、写下算式）；
- 至少 1200 中文/符号，杜绝三句话讲完一节。

## 1. 写作脚手架（每次动笔先搭这个）

1. **读原文**（整节！）——Book 原文（`data/` 或 PDF 提取）、Lean 文件逐条把定理名抄下来。
2. **列"这条要答什么"**：把这一节想解答的 3~5 个问题写出来（问题式大纲）。
3. **写核心论证草稿**：证明骨架、算 2 个数字例子，全部**先算完落在纸上**。
4. **对照 Lean**：对每一条"书的结论"，在 `analysis/...lean` 里找到对应声明（主题+行号），
   标成 `Lean: <file>:<line> <name>`。
5. **写**。按顺序、按框架（见 §2），一口气成稿，每段都要"顶天立地"（可独立读懂）。

## 2. 章节笔记框架：讲稿流 + 概念引导，不是总结流

**两条最高纪律：**
- **这是一篇连续讲稿，不是一张目录。** 禁止"动机段 → 定义列表 → 例子列表 → 定理列表"的零件陈列。
- **概念必须被"引导"出来，禁止被"宣布"出来。** 每个定义/定理登场前，读者必须先亲手经历"为什么非它不可"。总结式写法（"定义 1.2.2 如下""我们定义 X 为……"）是红牌。

### 2.0 概念引导法（guided emergence）——本 skill 的灵魂

每个重要定义必须走完这条四拍子的"重新发明"流程，写进正文：

```
第一拍 · 朴素方案   让读者先试显然的做法："你有一把尺子，想量 X。最自然的想法是……"
第二拍 · 失败诊断   让方案崩掉："但这对 X 行不通，因为……（给出具体反例/计算）"
第三拍 · 修补尝试   试一个改法："那换个思路：用……去逼近 X，取其极限——还是不行/行了一半……"
第四拍 · 概念的必然出场   宣告新定义时，让读者觉得它是被逼出来的：
                     "所以唯一的出路是允许……这就是我们要定义的 X。"
```

检查方法：删掉某个定义，前面铺垫的矛盾必须"爆炸"——读者读到这里应该自己喊出"那只能这么办了"。如果删掉定义段落读者毫无损失，说明你在宣布，不是引导。

**引导式文字的样子（示范，外测度）：**

> 你有一把尺子，量 [0,1] 得 1，(0,1) 也得 1——端点不算钱。现在想量 ℚ∩[0,1]：有理数。尺子只能量区间，而 ℚ∩[0,1] 千疮百孔，没有一段完整区间，无从下手。
>
> 绕路：不直接量它，用几个区间把它**盖**住，量盖子的总长，取最小的那种盖法。有理数可数，排好 q₁, q₂, …；给 qₙ 盖一个长 ε/2ⁿ 的区间，总长 = ε/2 + ε/4 + … = ε，想多小就多小。于是 ℚ∩[0,1] 的"最小盖长"= 0：可数个点加起来没有长度。
>
> 但注意：这里用了**可数无穷多个**盖子。若只允许有限个，ℚ∩[0,1] 盖不住（有限个正长区间拼不出一个不含任何区间段的集合的最小盖）。**把"有限个盒子"放宽成"可数个盒子"，就是 Lebesgue 外测度的全部发明**——Jordan 只允许有限个所以量不了 ℚ，Lebesgue 放开到可数个，一切活了。m* 不是被宣布的，是被这场盖盒子的实验逼出来的。

**反模式（一旦出现就是红牌）：**
- ❌ "定义 1.2.2：Lebesgue 外测度是……"（直接宣布，无铺垫）
- ❌ "下面我们介绍一个重要概念"（把引导机会变成介绍词）
- ❌ "不难证明……"（把失败诊断藏起来）


### 2.1 段落流的基本节奏

- **承上启下**：每段开头给出"为什么我们现在要干这个"——用"上一段这个反例让我们看到……，这促使我们……"这类过渡，禁止段落之间生切。
- **定义→立即检验**：给完一个定义，**同一个自然段或紧接的下一段**就用一个数字例子检验它（"比如取……，代入得……"），不要等三节之后才出现例子。
- **定理→立即消化**：证明完一个定理，紧接一段讲"这个定理在说什么、它回答了前面哪个问题、它给后面留了什么话头"，不要证完就跳到下一条。
- **问题和直觉先行**：任何定义/定理出现前，先让读者知道"这个问题长什么样、为什么现在要解决它"。

### 2.2 允许的文档结构（层级可以，但正文是散文）

```
（全文主体是连续散文：自然段接自然段，标题只在大转折处出现）

## 1 这一幕要解决什么          （动机，1-2 段——第一段不许出现"定义"二字）

## 2 精确定义与第一个例子      （散文：直觉 → 定义 → 立即检验的例子 → 反直觉点）

## 3 核心定理                   （散文：每个定理陈述 + 证明骨架 + 关键一步 + Lean 对照 + "这意味着什么"）

## 4 反直觉清单 / FAQ            （可以列表——这是查询性质的内容）

## 5 教材对照                    （表格——这是查询性质的内容）

## 6 Lean 对照表                 （表格——这是查询性质的内容）
```

关键分界：**正文（§1–§3）必须是散文流**；列表/表格只允许出现在查询性质的小节（FAQ、教材对照、Lean 表）。绝不允许正文变成"定义1：… 例子1：… 定理1：…"的流水账。

### 2.3 散文的腔调

- 用"我们""读者""注意到"的自然教学口吻，像在讲台上讲课，不是在做报表；
- 数字例子要"走一遍"：写出代入过程 `m*((0,1]) = 1 = |(0,1]|`，而不是"易得"；
- 段落长短混用：长段展开论证，短段一击中的；禁止全文等长段落；
- 一句话点破技巧："关键一步是反证法+紧致性抓子列"要放在证明骨架的**叙述里**，不是贴在末尾的标签。

## 3. 写作本身（文字）的规矩

### 3.1 数字与推导必须"真的写出来"

- 例子里所有算术必须完整：`1/(1.0001 − 1) = 10000` 而不能写"≈ 很大"；
- 每一个"——显然——"都必须替换成推导或反例。

### 3.2 第一个问题是 Why
每节以"为什么值得一节"开头；**第一段不许上"定义"二字**。

### 3.3 对照真实编号
- 书上的术语与编号（如"定义 9.1.5"）必须与 PDF 视图一致（核对 `第N章 页码`）；
- Lean 文件名写 `analysis/Section_9_3.lean`，行号必须从实际文件 grep 出来（不许猜）。

### 3.4 承认知识的边界
- 唯一"绝对正确"的声明=机器验证过的 Lean 定理；
- 未验证的结论：用"直观上／可以证明但不细写"分档，绝不说死。

### 3.5 文风：教材而不是简介（晚点交付检查单）
- 每个"定理"前面必须有一段**"为什么这定理看上去可信"**的直觉铺垫；
- 禁止空转段落："正如前面所说""这是一个重要的结果"（把"为什么重要"写实）；
- 禁止对照搬运——用"书上是这么说的"宁可不引；
- 禁止用"值得注意的"开头，直接写"注意：……"。

## 4. 步骤五（收尾）：自检清单（交付前逐条打勾）

- [ ] 开头 3 拍子：这一节的一切都与"为什么值得一节"挂钩；
- [ ] 定义：∀ 概念都有形式符号，且每个符号解释过一回；
- [ ] 至少 2 个可算例子 + 2 个反例/边界（有数字、有算式）；
- [ ] 每定理：意图 + 骨架 + 关键一步（而不是整套抄）；
- [ ] 每句"结论"要么给出推理要么标"待证"；
- [ ] Lean 对照行的每个 `file:line` 都从实际 grep 得到；
- [ ] 这篇笔记能独立于原书被读，不需要开第二本书；
- [ ] 未出现：3 行摘要、"不难看到"（而未给出看到了什么）、纯 bullet 罗列。

## 5. 简洁的（不该做的）

- 不许缩写成一个"马克down 摘要"：字数底线 1200 中文字（符号不算）；
- 不许用无内容的模板句填空（"本节深入探讨了……"是红牌）；
- 不许先给结论再给过程：一切"为什么"必须在结论**前**（或同段）给出。

## 6. 教师-学生循环（写完后必须经历的质疑）

初稿完成后，写手必须把稿子交给一个**完全不懂的学生**（`notes-student` subagent）读一遍。
学生的任务不是挑语法，而是：在每一个让他停下的地方，指出"这里缺了什么我才读不懂"。

对学生问题的处理规则：
- **必须逐条回应**：要么修改笔记消除疑问（改到学生能读下去），要么写 `不采纳：理由`。
- 学生重算出的数字和你不一致 → 一定是你错了，回去重算。
- "术语没定义就用" → 必须修。
- "为什么这样定义" → 如果笔记答不上来，说明动机没写透，修。
- 至少跑 1 轮；学生问题全部被回答（或合理拒绝）即停止，最多 2 轮。

这个循环的产出就是"教材级"的验收：**不是写手说自己写得好，而是学生读下来没问题。**

## 7. 交付格式

直接产出完整 Markdown（一只文件即可——就是 `notes/<dir>/<file>.md` 的内容），
不需要额外解释，不需要"我写好了"的壳。文件名与目录由主线程指定。
