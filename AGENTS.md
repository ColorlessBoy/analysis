# Lean 4 Workflows

The ONE authoritative workflow doc for this project. If `~/.opencode/skills/lean4/SKILL.md`
disagrees, THIS file wins (SKILL.md's claim that subagents lack MCP tools is wrong HERE —
verified 2026-07-26: subagents in this project DO have lean-lsp MCP access).

## Architecture (single source of truth)

| Component | Location | Rule |
|-----------|----------|------|
| Subagent definition | `.opencode/agents/lean-prover.md` | THE only definition. Do NOT add an inline `agent` block to `opencode.json` again (two definitions drifted and caused the steps:8 kill). |
| Subagent model | inherited default (deepseek-v4-flash) | Cheap on purpose → tasks MUST be small (≤100-line lemmas). |
| Subagent step limit | NONE | Never set `steps:` — an 8-step limit killed every proof mid-iteration ("跑一会就断了"). |
| MCP | `opencode.json` → `uvx lean-lsp-mcp` | Single-connection: max 1 concurrent subagent. |
| Prompt size | <21000 chars, generated by `subagent_prompt.py` | Prompts >3000 chars measurably return empty. Never paste the full contract into a prompt. |
| Temp files | `<project-root>/_temp_<name>.lean`, imports + ONE theorem | Small temp file = small diagnostics = subagent survives to completion. **Budget: keep each temp file ≤ ~300 lines; split/flush when it grows past ~500.** |

## The Workflow

```
TRIVIAL sorry (rfl/simp/norm_num, ≤3 lines)  → solve inline, no dispatch.
ANYTHING ELSE                                → dispatch lean-prover subagent.
```

1. `python3 .agents/scripts/sorry_status.py <file>` — locate sorries.
2. `lean_goal(file, line)` — read the goal. Estimate proof size.
3. **Main thread decomposes FIRST.** If the proof needs >100 lines, break it into
   ≤100-line lemmas in a temp file YOURSELF. Subagents cannot decompose — they get
   ONE lemma each, already isolated.
4. Generate prompt: `python3 .agents/scripts/subagent_prompt.py <file> <line> [--theorem N] [--deps F]`
5. Dispatch: `task(subagent_type="lean-prover", prompt=<generated>)`. NOT "general" —
   wrong agent type was another historical bug (config never applied).
6. Subagent returns `PROOF_BLOCK` → paste into real file →
   `lean_diagnostic_messages(real file)` → trust-but-verify → `git commit`.
7. Record: `python3 .agents/scripts/experience.py success add ...` (or `error add ...`).
8. FAIL → read the subagent's NOTES + temp file. Fix the APPROACH (smaller lemmas,
   different strategy), then dispatch a FRESH subagent. Never resume dead sessions.

## Temp-file size control (LSP feedback speed)

Every `lean_goal` / `lean_diagnostic_messages` call re-elaborates from the top of the
file. A large temp file (e.g. 1800 lines) turns every feedback cycle into repeated
60s `partial: true` polls — measured on `_temp_riemann.lean`. Rules:

- **Target ≤ ~300 lines per temp file**; treat ~500 as the hard ceiling.
- When a temp file grows past the budget (a subagent often accumulates 1000+ lines of
  helpers), **flush** it: move the already-compiling helper lemmas into the real file
  (before the target theorem), verify + commit, then continue in a fresh small temp
  file that imports the real file (which now contains the helpers). Do NOT keep growing
  the same temp file across sessions.
- For large work, **split into themed temp files** up front — e.g. `_temp_geom.lean`
  (measurability/geometry), `_temp_int.lean` (integral identity), `_temp_assembly.lean`
  (final theorems). Subagents work on ONE cluster file at a time; the main thread
  stitches cluster results into the real file and deletes the cluster files.
- A subagent that exceeds ~500 lines should stop and report partial helpers (compiling)
  so the main thread can flush, then be resumed on a fresh small file.

## LSP-first rules

| Task | ✅ USE | ❌ NEVER |
|------|--------|----------|
| Check errors | `lean_diagnostic_messages(file, timeout_s=30)` | `lake build` (60s vs 0.5s) |
| Proof state | `lean_goal(file, line, timeout_s=30)` | read + guess |
| Find lemmas | `lean_local_search("name")` | `grep` on .lean |
| Type of symbol | `lean_hover_info(file, line, col)` | guess |
| Test tactics | `lean_multi_attempt(file, line, snippets)` | blind edits |
| Read files | Read tool | `cat`/`head`/`tail` |
| Simple probes (`#check`/`#find`/`#eval`) | Write into temp file + read diagnostics (LSP cache is fast) | MCP round-trips |

`lake build` only at: cold start, after new `import`.

### Rebuild gate (mandatory, MCP-only)

After the main thread pastes a PROOF_BLOCK into the real file and diagnostics are clean
(0 errors, 0 warnings), run the **lean-lsp MCP rebuild** once as the final quality gate
before committing:

- `lean_build` (lean-lsp MCP, the `lsp_buildArguments` tool) — NOT `lake build` in a
  terminal. MCP rebuild restarts the LSP on the freshly built olean files, so the
  subsequent diagnostics reflect the real build.
- After the rebuild, re-run `lean_diagnostic_messages(real file)` once to confirm 0
  errors / 0 warnings, then commit.
- **Subagents NEVER rebuild.** Their whole loop is LSP diagnostics on the temp file;
  a rebuild adds nothing there. Rebuilding is exclusively the main thread's job, once,
  after integration. This keeps subagent cycles fast (no repeated 60s builds).

### Warning hygiene (ALL warnings/errors must be fixed)

Before a subagent returns a PROOF_BLOCK and before the main thread commits, the file
must have **0 errors and 0 warnings** (except the `declaration uses sorry` warnings
on still-open sorries). Every warning class gets fixed, none is exempt:

| Warning | Fix |
|---------|-----|
| Docstring/comment warnings or errors (verso parser choking on `{...}` braces, `_`-heavy identifiers, backticked code) | Rephrase, use `{lit}` roles, or drop the comment |
| `linter.unusedVariables` on an unused binder | Rename the binder to `_`-prefixed (`_hf`) — type-preserving, does not change the statement's meaning |
| `linter.unusedSimpArgs` / `linter.unnecessarySimpa` | Drop the unused simp argument / use plain `simp` |

The subagent MUST check `lean_diagnostic_messages` (including warnings) at the end and
fix all of them before returning. The main thread does the same after integration.

### Timeout / polling rule

When calling `lean_diagnostic_messages` or `lean_goal`, ALWAYS pass `timeout_s=30`.
If the response has `partial: true` (meaning the server is still elaborating),
poll again with `timeout_s=30` until `partial: false` or 10 retries.
A `partial` response does NOT mean there are 0 errors — it means the server hasn't
finished processing yet. Do NOT proceed to editing based on partial results.

## NEVER rules

| ❌ NEVER | ✅ ALWAYS |
|----------|----------|
| Set `steps:` on the lean-prover agent | Let it run until done |
| Define the same agent in opencode.json AND .opencode/agents/ | One definition: the agent file |
| Prompts >21000 chars / full contract pasted | `subagent_prompt.py` output as-is |
| Subagent on the real 2000-line file | Minimal temp file (imports + 1 theorem) |
| Growing a temp file past ~500 lines | Split/flush helpers to the real file; keep each temp ≤ ~300 lines |
| Parallel subagents | Max 1 — MCP is single-connection |
| Subagent edits real file | PROOF_BLOCK → main thread integrates |
| Multiple errors fixed at once | First error only, repeat |
| Ask subagent to decompose a big proof | Main thread decomposes BEFORE dispatch |
| Any warning/error returned in PROOF_BLOCK | 0 errors AND 0 warnings (fix unused binders via `_hf` renames, simp-arg warnings, docstrings) |
| MCP round-trips for `#check`/`#find`/`#eval` | Write probes in the temp file, read its LSP cache |
| Subagent runs `lean_build`/`lake build` | LSP diagnostics loop only; rebuild is main-thread-only, once, post-integration |

## Experience DB & Failure Tracking

Two files: `.agents/experience/db.json` (long-term tips) and `.agents/experience/failures.json` (per-session tracking).

```bash
python3 .agents/scripts/experience.py session start <thm> <file> <goal>   # new session → returns ID
python3 .agents/scripts/experience.py session attempt <id> "<edit>" <err_before> <err_after> "<excerpt>"
python3 .agents/scripts/experience.py session end <id> success|fail "notes"
python3 .agents/scripts/experience.py last 5                              # review recent sessions
python3 .agents/scripts/experience.py error search <topic>                # past failures on this topic
python3 .agents/scripts/experience.py tip list [--tag T]                  # heuristics BEFORE starting
python3 .agents/scripts/experience.py success add <thm> <file> <tactics> <desc>
python3 .agents/scripts/experience.py error add <file> <line> <type> <msg> [--solution ...]
python3 .agents/scripts/experience.py stats                               # health check
```

**Mandatory:** subagent MUST call `session start` before its first edit, `session attempt` after every edit, and `session end` when done. Main thread MUST call `last 5` before dispatching to learn from past failures.

## Convergence control

After each edit+verify cycle in the MAIN thread, if the file's error count strictly
increases 3 checkpoints in a row → STOP: `git stash`, re-read the theorem statement,
switch strategy (e.g. point-set proof → measure-theoretic proof), fresh subagent.

## Formalization self-doubt

Stuck >5 attempts on the same sorry? Question the STATEMENT, not the proof:
1. Try proving the negation — if easy, the statement is wrong.
2. Diff against the textbook PDF — missing hypothesis? wrong quantifier order?
3. Try a simplified version first.

## Notes writing pipeline (deep math notes)

For `notes/` chapter docs (NOT Lean proofs — different pipeline from the workflow above).

```
WRITE (notes-writer subagent, writes the target .md directly)
  → prompt: python3 .agents/scripts/notes_writer.py <type> <title> <target> --sources <lean files...>
  → agent reads .opencode/skills/deep-math-notes/SKILL.md + classics-crossref
  → returns short status report (DONE/NEEDS_HELP) — never the body in chat
STUDENT LOOP (teacher–student, max 2 rounds)
  → notes-writer dispatches notes-student (read-only naive learner) → gets QUESTIONS list
  → answers/edits note for every question (or 不采纳+理由) → re-runs self-check
REVIEW (notes-reviewer subagent, read-only: edit denied)
  → verifies every analysis/*.lean:NNN by grep, recomputes ≥2 example numbers,
    runs prose checks → VERDICT PASS / PASS-with-notes / FAIL + fix list
MAIN THREAD: apply fixes (or re-dispatch on FAIL) → re-read note once → git commit.
```

Rules that differ from the Lean workflow:
- Skills (not prompt text) carry the full standard — prompts stay ≤ ~2600 chars.
- Subagents write the note INTO the target file (there's no LSP edit-loop for markdown).
- `file:line` citations MUST be grep-verified twice (writer self-check + reviewer audit).
- Style rule: no AI-summary prose; ≥1200 chars; ≥2 worked examples; ≥1 counterexample.
- pacing: 1 subagent at a time (MCP single-connection applies to Lean LSP usage).
